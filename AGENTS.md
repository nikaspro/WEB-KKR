# AGENTS.md

Проект — предрелизный лендинг «Путешествовать — легко»: Vite, ванильный JavaScript, CSS и GSAP из npm.

## Главный принцип

**Стабильность уже работающего сайта важнее скорости изменений и красоты кода.**

Любая задача должна вносить минимально необходимое изменение.

Всё, что пользователь прямо не попросил изменить, должно остаться визуально и функционально таким же, как до правки.

Если не уверен, что изменение безопасно — не трогай этот код и ищи решение с меньшим радиусом воздействия.

**Одна задача → одна причина → минимальный патч → проверка → остановка.**

---

## Приоритеты

1. Сохранить утверждённые дизайн, контент, адаптив и хореографию.
2. Выполнить конкретный запрос владельца без побочных изменений.
3. Не создавать регрессии в уже работающих секциях.
4. Устранить ошибки, битые состояния и проблемы производительности.
5. Сокращать дубли, лишние запросы и работу главного потока только когда это относится к текущей задаче.
6. Не добавлять функции, которых нет в текущем сценарии.

---

## Минимальный радиус изменений

Если задача относится к конкретному блоку, элементу, анимации или состоянию:

- изменять только код, необходимый для этой задачи;
- не переписывать соседние блоки;
- не менять глобальные стили ради локальной проблемы;
- не делать рефакторинг «заодно»;
- не улучшать соседний код без прямого запроса;
- не переименовывать классы, функции и переменные без необходимости;
- не переносить код между файлами без необходимости;
- не менять архитектуру ради локальной задачи;
- не заменять рабочую реализацию на более «правильную», если текущая работает.

Если задачу можно решить локальным патчем — использовать локальный патч.

Если есть несколько решений, выбирать то, которое:

1. затрагивает меньше существующего кода;
2. влияет на меньшее количество секций;
3. проще проверить;
4. проще откатить;
5. меньше меняет существующее поведение.

---

## Сначала найти причину

Перед исправлением бага:

1. воспроизвести проблему;
2. определить конкретный код, который вызывает её;
3. проверить связанные стили, функции, timelines, ScrollTrigger и состояния;
4. понять причину;
5. только после этого менять код.

Не исправлять проблему серией случайных CSS/JS-патчей.

Не лечить симптом, если можно исправить первопричину.

Если простая визуальная проблема внезапно требует изменений в нескольких несвязанных системах проекта — пересмотреть решение перед продолжением.

---

## Сохранение существующего поведения

Без прямого запроса владельца не менять:

- текст;
- размеры;
- позиции;
- пропорции;
- отступы;
- типографику;
- цвета;
- структуру секций;
- порядок элементов;
- слои;
- hover/click состояния;
- адаптив;
- существующие анимации;
- easing;
- duration;
- stagger;
- тайминги;
- точки срабатывания;
- ScrollTrigger;
- pinned-поведение;
- содержимое экранов внутри mockup-устройств.

Отсутствие запроса на изменение считается требованием сохранить текущее поведение.

---

## Не создавать цепочку новых багов

Если после текущего изменения появился новый баг:

- сначала предположить, что причиной является текущий патч;
- не маскировать его следующим независимым патчем;
- не создавать цепочку компенсирующих CSS/JS-костылей;
- исправить исходное решение или отказаться от него;
- сравнить поведение с состоянием до правки.

Исправление нельзя считать успешным, если нужный элемент стал лучше, но соседняя часть сайта стала хуже.

---

## Не использовать случайные костыли

Без установленной причины проблемы не использовать как быстрый способ скрыть баг:

- случайное увеличение `z-index`;
- `!important`;
- отрицательные margin;
- дополнительные `transform`;
- `overflow: hidden`;
- абсолютное позиционирование вместо исправления layout;
- дополнительные таймеры;
- дополнительные ScrollTrigger;
- дополнительные resize/scroll/mousemove listeners.

Эти инструменты допустимы, если являются частью осознанного решения.

## Структура и организация кода

- `index.html` — единственная рабочая страница и содержит только разметку.
- Стили находятся в `src/styles/`, логика и анимации — в `src/scene/`.
- `src/scene/phases.js` — единый источник окон и таймингов фаз.
- `public/assets/` — локальные шрифты, медиа и embedded-экран.
- `legacy/rd-hero-v4.html` — только совместимый переход на корневую страницу, не вторая реализация.

Ориентиры:

- HTML — до 500 строк;
- JS — до 2000 строк;
- CSS — до 2000 строк.

При превышении ориентира сначала удалить мёртвый код, дубли и лишние условия.

Если файл всё ещё слишком большой — разделить по независимым зонам ответственности.

Не дробить код на множество маленьких файлов без практической необходимости.

Не создавать вторую реализацию существующего блока.

Не держать старую и новую версии одной функции, сцены или анимации одновременно.

Не добавлять временные файлы, копии, архивы, build-артефакты и неиспользуемые ассеты.

Исходники остаются читаемыми; минификацию выполняет production-сборка Vite.

Не вводить React, Vue, TypeScript, SSR, CMS, роутер или новую архитектуру без прямой необходимости.

---

## Переиспользование

До реализации проверить существующие:

- компоненты;
- функции;
- стили;
- селекторы;
- переменные;
- GSAP timelines;
- ассеты.

Не переизобретать уже существующую механику.

Для новых секций переиспользовать имеющиеся паттерны адаптива, состояний, easing и управления скроллом.

Если нужный эффект уже существует — переиспользовать или аккуратно расширить существующую реализацию.

### Переиспользование анимаций

Перед созданием новой анимации сначала проверить, как аналогичный элемент уже анимируется на сайте.

Если существующий паттерн подходит — переиспользовать его.

По умолчанию одинаковые типы элементов должны анимироваться одинаково:

- заголовки — одним принципом;
- основной текст — одним принципом;
- похожие карточки — одинаково;
- повторяющиеся кнопки и элементы интерфейса — одинаково;
- похожие переходы между секциями — на основе уже существующей механики.

Не создавать новый способ появления текста, карточек, кнопок или других повторяющихся элементов, если пользователь прямо не попросил новый эффект.

Если в одной части сайта уже утверждён конкретный способ появления текста, использовать его как стандарт для аналогичного текста в других секциях.

Уникальную анимацию создавать только если:

- пользователь прямо попросил новый эффект;
- элемент по сценарию действительно требует отдельной хореографии;
- существующая механика технически не подходит.

Цель — единая система движения по всему сайту, а не набор разных эффектов.

## Имена начертаний Nunito Sans

- `Nunito Light Wide` — класс `.font-nunito-light-wide`: normal, weight 300, stretch 105%, YTLC 500.
- `Nunito Medium` — класс `.font-nunito-medium`: normal, weight 500, обычная ширина.

По запросу владельца с одним из этих имён применять соответствующий класс или тот же набор CSS-свойств.

Не подменять его соседним весом.

Оси каждого начертания зафиксированы внутри отдельного статического WOFF2, поэтому `font-variation-settings` при применении не требуется.

## Предрелизный режим

Новая строка кода должна решать конкретную видимую проблему или обязательную предрелизную проверку.

Не добавлять функции, которых нет в текущем сценарии.

В рамках технической оптимизации не менять:

- текст;
- размеры;
- позиции;
- пропорции;
- цвета;
- easing;
- stagger;
- тайминги;
- порядок элементов.

Все интерактивные элементы должны иметь корректные состояния и не оставаться необозначенными визуальными заглушками.

Все внутренние ссылки должны вести к существующим секциям.

В консоли не должно быть ошибок и предупреждений проекта.

Страница должна работать на:

- desktop;
- mobile;
- нестандартных соотношениях сторон;
- `prefers-reduced-motion`;
- базовом уровне без JavaScript.

Никаких внешних runtime-ресурсов: шрифты, GSAP и медиа только локальные.

Не добавлять зависимости без прямого согласования.

Изменять лимиты `budget.json` только по прямому решению владельца.

## Ассеты и производительность

- Никаких `data:` длиннее 2 КБ.
- Изображения и SVG хранить отдельными файлами.
- Все изображения имеют `width` и `height`.
- Контент вне первого экрана использует `loading="lazy"`.
- Видео: `preload="none"`, `poster`, muted и без загрузки до входа в сцену.
- Не использовать полноэкранный `mix-blend-mode`.
- Не использовать движущийся `filter: blur()`.
- Не использовать постоянный `will-change` в CSS.

В одном кадре:

1. проверить активность;
2. прочитать DOM;
3. рассчитать состояние;
4. записать свойства.

Не чередовать layout read/write.

Кэшировать DOM и отключать работу вне активной фазы.

---

## GSAP и скролл

GSAP и ScrollTrigger импортируются из npm и регистрируются один раз.

Подробные правила находятся в `GSAP.md`.

Без прямого запроса не менять:

- easing;
- duration;
- stagger;
- точки срабатывания;
- порядок элементов;
- количество элементов;
- хореографию существующих сцен.

Не создавать новый timeline или ScrollTrigger, если нужное поведение можно получить переиспользованием или расширением существующей анимации.

Не создавать новую анимацию, если эффект уже реализован существующим timeline.

Не менять общую timeline ради локальной анимации одного элемента.

Фазы не пересекаются, кроме явно разрешённых overlap в `src/scene/phases.js`.

Использовать общий `gsap.ticker`.

Не создавать параллельные покадровые циклы без необходимости.

`ScrollTrigger.refresh()`:

- не вызывать в scroll;
- не вызывать в resize без debounce;
- никогда не вызывать в покадровом цикле.

`prefers-reduced-motion` должен показывать понятное статичное состояние без scrub-анимации.

## Проверка после изменения

После любой визуальной или функциональной правки проверить не только изменённый элемент.

Минимальная зона проверки:

1. состояние непосредственно перед изменённой секцией;
2. вход в изменённую секцию;
3. основное состояние секции;
4. выход из неё;
5. переход в следующую секцию.

Если используется обратный скролл — проверить возвращение назад.

Если изменение связано с GSAP/ScrollTrigger:

- проверить начало сцены;
- середину;
- конец;
- обратный скролл;
- отсутствие скачков;
- отсутствие преждевременного исчезновения элементов;
- отсутствие конфликтов с соседней фазой.

Если изменение затрагивает layout, размеры, viewport units, позиционирование или media queries — проверить mobile.

При изменении JavaScript проверить отсутствие новых ошибок в консоли.

Не считать задачу завершённой только потому, что нужный элемент выглядит правильно в одном состоянии.

---

## Быстрые визуальные итерации

Пока владелец вносит визуальные правки по секциям, по умолчанию работать в быстром режиме.

Полный предрелизный режим включать по прямому запросу или перед публикацией.

В быстром режиме проверять:

- затронутую секцию;
- вход из предыдущей секции;
- переход в следующую секцию;
- консоль, если менялся JavaScript.

Mobile проверять только если изменение способно повлиять на:

- layout;
- размеры;
- позиционирование;
- viewport units;
- responsive CSS;
- поведение элементов на узком экране.

Не тратить время после каждой маленькой правки на:

- полный аудит mobile;
- нестандартные viewport;
- `prefers-reduced-motion`;
- режим без JavaScript;
- budget;
- legacy;
- полный `npm run check`.

Для правок только HTML/CSS не запускать production-сборку после каждой итерации.

При изменении JavaScript выполнить минимум:

`node --check <file>`

Если правка создаёт явный риск runtime-ошибки — выполнить минимальную целевую проверку.

Полный `npm run check`, адаптив, reduced motion, консоль, страницу без JavaScript и GitHub Pages проверить один раз на финальном предрелизном рубеже.

## Рабочий порядок

1. Прочитать `AGENTS.md`.
2. Если задача касается анимаций — прочитать `GSAP.md`.
3. Проверить `git status`.
4. Изучить существующую реализацию задачи.
5. Определить минимальный набор файлов и кода для изменения.
6. Найти причину проблемы до внесения патча.
7. Сделать минимальное изменение.
8. Проверить изменённую секцию и ближайшие переходы.
9. Для изменённого JS выполнить `node --check <file>`.
10. Убедиться, что изменение не создало новых регрессий.
11. После выполнения запроса остановиться.

В полном предрелизном режиме выполнить `npm run check`: build, budget, phases и legacy.

Перед публикацией проверить desktop, mobile, нестандартный viewport, reduced motion, консоль и страницу без JS.

Убедиться, что GitHub Pages открывается со всеми локальными ассетами.

---

## Стоп после выполнения задачи

Когда запрос владельца выполнен и проверен — остановиться.

Без прямого запроса не продолжать:

- улучшать дизайн;
- рефакторить;
- оптимизировать соседний код;
- менять существующие анимации;
- чистить файлы;
- переименовывать сущности;
- исправлять другие замеченные проблемы;
- добавлять новые функции.

Не расширять самостоятельно scope задачи.

---

## Итоговый отчёт

После выполнения задачи кратко указать:

- что изменено;
- какие файлы изменены;
- что было проверено;
- затронуты ли визуал или хореография;
- есть ли что-то, что не удалось проверить.

Для полного предрелизного аудита дополнительно указать:

- исправленные ссылки;
- удалённые дубли;
- оставшиеся продуктовые заглушки;
- превышения ориентиров по строкам;
- безопасную схему будущего разделения;
- вес JS;
- вес критического пути;
- вес страницы целиком.

Без прямого запроса:

- не выполнять force push;
- не менять `main`;
- не удалять пользовательские данные;
- не добавлять функции.
