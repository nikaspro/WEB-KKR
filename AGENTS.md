# AGENTS.md

Правила для всех, кто трогает этот репозиторий — людей и агентов. Читать до первой правки.

## 0. Главный принцип

Сайт должен быть быстрым на слабых устройствах. Из этого следует всё остальное.

Приоритет при конфликте требований:

1. Визуальный результат анимации не меняется.
2. Бюджет производительности соблюдается.
3. Проект остаётся простым.

Если требования конфликтуют так, что одно нельзя выполнить без нарушения другого — не решать самостоятельно, спросить владельца.

## 1. Анимация неприкосновенна

Оптимизируется **цена** анимации, а не сама анимация. Визуальный результат — инвариант.
Главный враг ощущения от сцены — не тяжёлый код, а дёрганье: сцена, роняющая кадры,
ощущается хуже той же сцены, идущей ровно.

### Эталон

До первой правки, затрагивающей сцену, фиксируется эталон в `docs/baseline/`:

- видео полной прокрутки страницы — тот же viewport, DPR 2, та же длительность;
- performance-трейс DevTools за ту же прокрутку;
- `docs/baseline/animation.md` — таблица: элемент, свойство, длительность, easing,
  задержка/stagger, точка срабатывания (scroll offset или триггер).

Без эталона фраза «стало как было» непроверяема. Правки сцены без зафиксированного
эталона не принимаются.

### Разрешено без согласования — результат пиксельно идентичен

- то же движение через `transform`/`opacity` вместо `width`/`height`/`top`/`left`/`margin`;
- одна `requestAnimationFrame`-петля вместо нескольких;
- чтение layout один раз за кадр, без чередования read → write;
- пассивные обработчики скролла; точечный `will-change` со снятием после анимации;
- ленивая инициализация сцены при подходе к вьюпорту вместо работы на старте;
- `content-visibility: auto` на секциях вне экрана;
- подключение только используемых модулей GSAP;
- картинки, шрифты, мёртвый CSS и JS — к хореографии не относятся.

### Требует явного согласования владельца

Любое изменение длительностей, кривых easing, stagger, точек срабатывания, количества
анимируемых элементов, а также замена GSAP на нативные средства. Показывать два варианта
рядом; решение принимает владелец, не исполнитель.

## 2. Бюджет

Все веса — **transferred (brotli)**. Raw-размер указывается в отчёте справочно.

| Ресурс | Лимит |
|---|---|
| HTML | 15 КБ |
| CSS | 40 КБ, из них критические инлайном ≤ 10 КБ |
| JS | 100 КБ |
| Шрифты | 100 КБ, только woff2, сабсет, ≤ 2 файла |
| Картинки первого экрана | 150 КБ |
| Первый экран целиком | 200 КБ |
| Страница целиком со всеми ассетами | 900 КБ |
| Сторонние домены | 0 |

Первый экран = render-blocking CSS/JS + шрифты первого экрана + LCP-изображение.

| Метрика | Цель |
|---|---|
| LCP, Slow 4G | ≤ 2.0 s |
| LCP, Slow 3G + CPU x4 | ≤ 3.5 s |
| CLS | ≤ 0.1 |
| Long tasks > 50 мс | 0 на загрузке и на скролле |
| fps на скролле, DPR 2 | 60; на слабом устройстве ≥ 30, без фризов > 100 мс |
| Скрипт на кадр сцены | ≤ 4 мс |

Правила измерения: медиана из 5 прогонов на фиксированном пресете троттлинга.
Одиночный прогон результатом не является.

`npm run budget` проверяет веса и падает с кодом 1 при превышении. Скрипт — на голом
Node, без зависимостей (`zlib` из стандартной библиотеки), поэтому не добавляет
пользователю ни байта. «Потом померим» не существует: превышение — красный гейт.

fps и кадровый бюджет автоматизации не поддаются: проверяются трейсом вручную перед
мержем, трейс прикладывается к PR.

Превышение лимита закрывается сокращением работы, а не поднятием лимита. Режем фазу,
а не покупаем железо. Сами лимиты меняет только владелец.

## 3. Простота

Запрещено: React, Vue, Svelte, сборка TypeScript, SSR, CMS, клиентский роутер, WebGL,
Three.js, шейдеры, физические движки.

Сцена — DOM и трансформы. В анимации допустимы только `transform` и `opacity`:
`width`, `height`, `top`, `left`, `margin` в анимации означают layout на каждом кадре,
и бюджет 4 мс не удержать даже без зависимостей.

Зависимости: GSAP — единственная рантайм-зависимость. Любая новая — только с обоснованием
и замером веса до/после в описании PR. Это правило распространяется и на GSAP: ядро плюс
ScrollTrigger — порядка 36 КБ gzip, то есть больше трети бюджета JS. Если он используется
только для появлений элементов при скролле, он обязан уступить `IntersectionObserver`
плюс CSS-переходам, которые дают тот же результат за 0 КБ. Он остаётся там, где нужен
настоящий таймлайн: секвенирование, скраб по прогрессу, снэппинг.

Типы: сборка TypeScript не вводится — её цена не в весе, а в build-step. Вместо неё
`// @ts-check` и типы в JSDoc: проверка в редакторе при нулевой сборке и нулевом весе,
ловит опечатки в селекторах и обращения к `null`.

Кастомный эффект — только если готовое не подошло, и только с фолбэком. Фолбэк по
feature detection, никогда по User-Agent.

## 4. LITE

Второй версии страницы под мобильные нет. Есть один флаг `LITE` и ветки внутри тех же
модулей.

- **Направление безопасное:** по умолчанию лёгкий путь, тяжёлые фазы добавляются сверху.
  Неопознанное устройство получает быстрый вариант, а не тяжёлый.
- **Флаг читается один раз при загрузке и замораживается.** Переоценка на `resize`
  запрещена: поворот экрана и появление адресной строки не должны переключать ветки —
  это гарантированные фризы.
- Сигналы: `prefers-reduced-motion`, `hardwareConcurrency`, `deviceMemory`,
  `connection.saveData`.
- **Ветки — на входе в фазу**, а не внутри покадрового цикла: фаза включается или
  пропускается целиком. Это и меньше кода под тестирование.
- Что деградирует в LITE: `blur` и `box-shadow` на движущихся слоях, число параллакс-слоёв,
  количество одновременно анимируемых элементов. Хореография — те же элементы, те же
  кривые, та же последовательность — сохраняется. На нормальном устройстве сцена идёт
  без изъятий.

## 5. Чеклист перед коммитом

- [ ] `npm run budget` зелёный
- [ ] LCP измерен: медиана из 5 прогонов, оба пресета
- [ ] снят трейс скролла: кадр сцены ≤ 4 мс, long tasks отсутствуют
- [ ] сравнение с эталоном: хореография не изменилась
- [ ] консоль без ошибок и предупреждений
- [ ] проверено с JS и без него, при `prefers-reduced-motion`, в LITE и в полном режиме
- [ ] нет новых зависимостей и сторонних домен без обоснования в PR
- [ ] в PR указаны веса до/после и цифры метрик

Формат отчёта о любой правке: **что нашёл → что изменил → зачем → вес и метрика до/после.**
